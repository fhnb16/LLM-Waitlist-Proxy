# ТЗ: сервер очереди нейросети для UniversalBot

Документ для агента-разработчика. Задача — написать с нуля **сервер очереди**. Он стоит между
Telegram-ботом UniversalBot и локальными моделями (llama.cpp, vLLM, Ollama и т. п.), принимает задания,
выполняет их по очереди и возвращает ответ боту. Старый сервер очереди выбрасывается: протокол 1
поддерживается только для совместимости (раздел 9).

Сторона бота **уже реализована** и покрыта тестами (`tests/QueueProtocolTest.php`). Сервер должен
соответствовать контракту ниже буквально.

---

## 1. Зачем нужен сервер

- Локальная модель на одной видеокарте отвечает 10–120 с и обслуживает 1–4 запроса одновременно.
- Бот получает обновления вебхуком на PHP-хостинге. Обработку бот ведёт после ответа Telegram, но
  PHP-процесс ограничен ~180 с, и держать его минутами нельзя. Есть ещё и Cloudflare Worker перед ботом.
- Поэтому бот **ставит задание** и сразу освобождается. Сервер считает ответ и **присылает результат
  обратно** на `https://<бот>/webhook/llm`, а бот сам отправляет его в Telegram.

```
Telegram ──вебхук──▶ Бот (PHP) ──POST задание──▶ Сервер очереди ──▶ Модель (OpenAI-совместимый API)
   ▲                    │  ◀── 202 "Added to queue"        │
   │                    │                                   │ (секунды…минуты)
   └── sendMessage ◀─── Бот ◀── POST результат (/webhook/llm, токен) ──┘
```

Ключевые принципы:
1. **Сервер не знает токена бота и не ходит в Telegram** (в протоколе 2). Форматирование, темы форума,
   ответ реплаем, память и история остаются на стороне бота.
2. **Принять задание — быстро** (< 1 с), **выполнить — надёжно**: очередь переживает перезапуск, доставка
   «хотя бы один раз», бот отбрасывает повторы по `job_id`.
3. Сервер — **OpenAI-совместимый** для бота: тот же адрес `…/v1/chat/completions`, те же поля, плюс поля очереди.

## 2. Контракт: бот → сервер (постановка задания)

### 2.1. Запрос

```
POST {endpoint}                 обычно https://queue.example.com/v1/chat/completions
Authorization: Bearer <API_KEY> ключ клиента (в боте — поле «API-ключ» провайдера)
Content-Type: application/json
```

Тело — запрос OpenAI Chat Completions плюс поля очереди:

```json
{
  "model": "qwen3-27b",
  "messages": [
    {"role": "system", "content": "…"},
    {"role": "user", "content": "…"}
  ],
  "temperature": 0.7,
  "max_tokens": 400,
  "stream": false,

  "protocol": 2,
  "delivery": "bot",
  "job_id": "3f9c1a2b4d5e6f708192a3b4",
  "chat_id": -1001234567890,
  "reply_to": 4711,
  "thread_id": null,
  "callback": {"url": "https://bot.example.com/webhook/llm", "token": "…"}
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `model` | string | Имя модели. Бот берёт его из списка `GET /v1/models` (п. 4.1) или из настроек. |
| `messages` | array | Сообщения OpenAI. `content` — строка **или** массив частей (`{"type":"text"}`, `{"type":"image_url","image_url":{"url":"data:image/jpeg;base64,…"}}`) для vision. |
| остальные параметры | any | Всё из «Параметров запроса» провайдера в боте: `temperature`, `top_p`, `top_k`, `max_tokens`, `stop`, `reasoning_effort`, `chat_template_kwargs`… **Передавать в модель как есть**, не отбрасывать неизвестные. |
| `stream` | bool | Для протокола 2 всегда `false`. Сервер сам решает, как говорить с моделью. |
| `protocol` | int | `2` — новый протокол (по умолчанию). `1` — старый (раздел 9). |
| `delivery` | string | `"bot"` — вернуть текст боту (протокол 2). `"telegram"` — старое поведение. |
| `job_id` | string | ≤ 64 символа `[A-Za-z0-9_-]`. **Ключ идемпотентности**: повтор с тем же `job_id` не создаёт второе задание. |
| `chat_id` | int\|null | Чат Telegram. `0` или отсутствует → **синхронный режим** (п. 2.3). |
| `reply_to` | int\|null | На какое сообщение отвечать. Сервер только возвращает его обратно. |
| `thread_id` | int\|null | Тема форума. Сервер только возвращает его обратно. |
| `callback.url` | string | Куда прислать результат. **Проверять по белому списку хостов** (п. 7). |
| `callback.token` | string | Токен для заголовка `X-Callback-Token` при обратном вызове. |

Если `callback` не пришёл (у бота не задан публичный адрес), используются `BOT_CALLBACK_URL` и
`BOT_CALLBACK_TOKEN` из конфигурации сервера.

### 2.2. Ответы на постановку

| Ситуация | Код | Тело | Что сделает бот |
|---|---|---|---|
| Принято в очередь | `202` (или `200`) | `{"status": "Added to queue", "job_id": "…", "position": 3, "eta_seconds": 40}` | Ничего не отправляет, ждёт обратного вызова. **Строка `status` обязательна дословно** (регистр не важен). |
| Повтор того же `job_id` | `200` | то же, что при первой постановке (текущий статус) | — |
| Неверный ключ | `401` | `{"error": {"message": "invalid api key"}}` | Пробует следующую модель или провайдера. |
| Неизвестная модель | `400` | `{"error": {"message": "unknown model 'x'"}}` | Пробует следующую модель или провайдера. |
| Очередь переполнена, лимит клиента | `429` + `Retry-After: <сек>` | `{"error": {"message": "queue is full"}}` | Ставит эту модель на паузу на `Retry-After` и идёт к резервной модели или провайдеру. |
| Сервер перегружен, модели недоступны | `503` + `Retry-After` | `{"error": {"message": "…"}}` | То же. |
| Тело слишком большое | `413` | `{"error": {…}}` | — |

Ответ на постановку должен приходить **меньше чем за 1 с**: бот ждёт не дольше таймаута провайдера,
а время на весь ответ ограничено 150 с.

### 2.3. Синхронный режим (`chat_id` = 0 или отсутствует)

Так бот вызывает сервер из панели: «Проверить» в карточке провайдера и «Песочница». Сервер выполняет
запрос **сразу**, с приоритетом выше обычных заданий, и отвечает обычным ответом OpenAI:

```json
{"id": "…", "object": "chat.completion", "model": "qwen3-27b",
 "choices": [{"index": 0, "message": {"role": "assistant", "content": "OK"}, "finish_reason": "stop"}],
 "usage": {"prompt_tokens": 12, "completion_tokens": 1, "total_tokens": 13}}
```

Таймаут синхронного режима — `SYNC_TIMEOUT` (по умолчанию 60 с). Если не успел — `504` с `error.message`.
Обратный вызов в синхронном режиме **не делается никогда**.

## 3. Контракт: сервер → бот (результат)

### 3.1. Запрос

```
POST {callback.url}                    обычно https://bot.example.com/webhook/llm
X-Callback-Token: {callback.token}     (старый вариант ?token=… тоже принимается ботом, но не использовать)
Content-Type: application/json
```

Успех:

```json
{
  "job_id": "3f9c1a2b4d5e6f708192a3b4",
  "chat_id": -1001234567890,
  "reply_to": 4711,
  "thread_id": null,
  "text": "Ответ модели как есть",
  "model": "qwen3-27b",
  "usage": {"prompt_tokens": 1830, "completion_tokens": 96, "total_tokens": 1926},
  "queued_ms": 12500,
  "latency_ms": 18400
}
```

Ошибка:

```json
{"job_id": "…", "chat_id": -100…, "reply_to": 4711, "thread_id": null,
 "text": null, "error": "upstream timeout after 120s", "error_code": "upstream_timeout"}
```

| `error_code` | Когда | Что сделает бот |
|---|---|---|
| `upstream_error`, `upstream_timeout`, `empty_answer` | модель не ответила | Отправит «Текст, если модели не ответили» (если он задан). |
| `expired` | задание ждало дольше `MAX_WAIT` | **Промолчит.** |
| `cancelled` | отменено через API (п. 4.3) | Промолчит. |
| `superseded` | вытеснено более новым заданием того же чата (п. 5.3) | Промолчит. |

`text` передавать **сырым**: бот сам вырежет `<think>…</think>`, служебные токены, метки памяти
`[[запомнить: …]]` и переведёт Markdown в HTML Telegram. Если модель вернула `reasoning_content` отдельно от
`content`, в `text` идёт только `content`.

### 3.2. Ответ бота и повторы

- Бот отвечает `200` сразу, ещё до отправки в Telegram. Любой `2xx` — доставлено.
- `403` — неверный токен: **не повторять**, задание в `dead` с ошибкой `callback_forbidden`, предупреждение в журнал.
- Сетевая ошибка, `5xx`, `429` — повторять с паузами 2, 5, 15, 30, 60 с (не больше `CALLBACK_RETRIES`,
  по умолчанию 6), потом `dead`.
- Бот **отбрасывает повторы** по `job_id` (двое суток), поэтому повторная доставка безопасна.

## 4. Дополнительные эндпоинты

Все под `Authorization: Bearer <API_KEY>`, кроме `/healthz`.

### 4.1. `GET /v1/models` — **обязательно**

Кнопка «Загрузить модели» в боте вызывает `GET {base}/models`, где `base` — адрес провайдера без
`/chat/completions`. Ответ в формате OpenAI, список — из таблицы маршрутизации моделей (п. 5.4):

```json
{"object": "list", "data": [{"id": "qwen3-27b", "object": "model", "owned_by": "local"}, {"id": "gpt-oss-20b", "object": "model"}]}
```

### 4.2. `GET /v1/jobs/{job_id}`

Статус задания: `queued | running | done | failed | expired | cancelled | superseded | dead`,
позиция в очереди, время, модель, ошибка. Текст ответа не возвращать: он уже ушёл боту и может быть
персональным.

### 4.3. `DELETE /v1/jobs/{job_id}`

Отменить задание в очереди. Если оно уже выполняется — прервать запрос к модели. Боту отправить `error_code: cancelled`.

### 4.4. `GET /v1/queue`

Сводка: длина очереди по моделям, сколько выполняется, среднее ожидание и время ответа за 5, 60 мин.

### 4.5. `GET /healthz` (без авторизации)

`200 {"ok": true}`, если база доступна и хотя бы одна модель отвечает. Иначе `503`. Без подробностей.

### 4.6. `GET /metrics` (Prometheus, по желанию; закрыть токеном или сетью)

`queue_jobs{state}`, `queue_wait_seconds` (гистограмма), `upstream_latency_seconds{model}`,
`upstream_errors_total{model,code}`, `callback_failures_total`.

## 5. Как работает очередь

### 5.1. Хранение

- Задания хранятся **на диске** (SQLite в режиме WAL достаточно; Redis — по желанию).
- После перезапуска `queued` остаются в очереди. Задания `running` на момент падения возвращаются в
  `queued`, если не исчерпаны попытки.
- Таблица заданий: `job_id` (уникальный), `client`, `model`, `chat_id`, `reply_to`, `thread_id`,
  `payload` (тело для модели), `callback_url`, `callback_token` (хранить зашифрованным или хотя бы не
  логировать), `state`, `attempts`, `created_at`, `started_at`, `finished_at`, `error`, `error_code`,
  `usage`, `result_text` (удалять после доставки).
- Чистка: завершённые старше `RETENTION_HOURS` (24) удаляются вместе с текстами.

### 5.2. Порядок и параллельность

- **Слоты на модель**: у каждой модели свой лимит одновременных запросов (`slots`, равен `--parallel`
  у llama.cpp). Пока слот занят, задания этой модели ждут.
- **Один чат — одно задание одновременно.** Следующее задание того же `chat_id` не начинается, пока не
  закончилось предыдущее, иначе ответы перепутаются по порядку.
- **Справедливость**: при длинной очереди задания разных чатов чередуются (round-robin по `chat_id`),
  чтобы один шумный чат не занял всё.
- **Приоритет**: синхронный режим выше всех. Личные чаты (`chat_id > 0`) выше групп (настраивается).

### 5.3. Ограничения времени

- `MAX_WAIT` (по умолчанию 300 с): задание, не начавшееся за это время, завершается с `error_code: expired`
  (бот промолчит). Отвечать в чат через 10 минут хуже, чем не отвечать.
- `UPSTREAM_TIMEOUT` (по умолчанию 120 с) на один запрос к модели.
- **Вытеснение** (`SUPERSEDE_SAME_CHAT`, по умолчанию выключено): если в очереди **ещё не начатое**
  задание чата, а пришло новое из того же чата, старое завершается с `superseded`.
- Лимит очереди: `MAX_QUEUE` (200) всего и `MAX_QUEUE_PER_CHAT` (5). Сверх — `429` с `Retry-After`.

### 5.4. Модели (апстримы)

Таблица маршрутизации в конфиге:

```yaml
models:
  qwen3-27b:
    upstreams:
      - url: http://127.0.0.1:8080/v1/chat/completions   # llama.cpp
        model: qwen3-27b-q4_k_m                           # имя, которое ждёт апстрим (по умолчанию = ключу)
        api_key: ""
        slots: 2
    defaults: {max_tokens: 400}        # подставляются, если бот их не прислал
    force: {}                          # перекрывают присланное (например, chat_template_kwargs)
  gpt-oss-20b:
    upstreams:
      - url: http://127.0.0.1:8081/v1/chat/completions
        slots: 1
    defaults: {reasoning_effort: low}
```

- Неизвестная модель → `400` (бот перейдёт к резервной).
- Несколько апстримов у модели: по очереди при ошибке соединения или `5xx`; `4xx` — ошибка задания.
- Повтор задания при `upstream_error`: до `UPSTREAM_RETRIES` (1) раз, потом ошибка боту.
- Пустой `content` после удаления `<think>` → `error_code: empty_answer`.
- Запрос к апстриму — без `stream` или со стримом с внутренней сборкой ответа, на выбор реализации.
  Из ответа брать `choices[0].message.content`; если пусто — `choices[0].text`.

## 7. Безопасность

- **Авторизация клиентов** по `Authorization: Bearer`, сравнение за постоянное время. Несколько ключей с
  именами (имя пишется в журнал и метрики). `401` без подробностей.
- **SSRF**: `callback.url` — только `https://` (или `http://` для `localhost` и частных сетей, если явно
  разрешено) и только хосты из `CALLBACK_ALLOWED_HOSTS`. Иначе задание отклоняется с `400`.
- **Секреты**: ключи клиентов, токены обратного вызова и ключи апстримов никогда не попадают в журнал и
  ответы API. Токен обратного вызова хранить зашифрованным (ключ — `SECRET_KEY` из окружения) или
  удалять сразу после доставки.
- **Персональные данные**: тексты сообщений не логировать (`LOG_CONTENT=false`). `result_text` и
  `payload` удалять после доставки или по сроку хранения.
- Пределы размера тела, числа сообщений и длины строк. На тяжёлые операции — защита от «медленных» клиентов
  (таймауты чтения тела).
- Сервер слушает локальный адрес, наружу его публикует обратный прокси (nginx или Caddy) с TLS.

## 8. Реализация

**Рекомендуемый стек** (можно другой, если удобнее, — главное соблюсти контракт):
Python 3.12, FastAPI + uvicorn, httpx (async), SQLite (aiosqlite) в WAL, pydantic-settings, pytest +
respx/pytest-httpx для тестов. Один процесс: HTTP-приём плюс асинхронный диспетчер воркеров по слотам.

Структура:

```
queue-server/
  app/
    main.py          # FastAPI: маршруты (2, 4), авторизация
    models.py        # pydantic-схемы запросов/ответов
    store.py         # SQLite: задания, состояния, миграции схемы
    dispatcher.py    # выбор следующего задания: слоты, один чат — одно задание, round-robin, приоритеты, истечение
    upstream.py      # вызов OpenAI-совместимого апстрима, перебор апстримов, повторы, разбор ответа
    callback.py      # доставка результата боту, повторы, белый список хостов
    config.py        # окружение + config.yaml
    metrics.py
  tests/
  config.example.yaml
  Dockerfile
  docker-compose.example.yml   # сервер + llama.cpp
  README.md
```

Жизненный цикл задания:

```
queued ──▶ running ──▶ done ──(колбэк 2xx)──▶ delivered (result_text стёрт)
   │          │                └─(повторы исчерпаны / 403)──▶ dead
   │          └──▶ failed ──(колбэк с error)──▶ delivered | dead
   ├──▶ expired    (MAX_WAIT)    ──колбэк error_code=expired
   ├──▶ cancelled  (DELETE)      ──колбэк error_code=cancelled
   └──▶ superseded (новое задание того же чата) ──колбэк error_code=superseded
```

Журнал — JSON-строками: `job_id`, `client`, `model`, `chat_id`, `state`, `wait_ms`, `latency_ms`,
`tokens`, `error_code`. Без текстов.

## 9. Совместимость со старым протоколом (по желанию)

Если в задании `protocol: 1` / `delivery: "telegram"` (в боте — параметр провайдера `"_delivery": "telegram"`):

- сервер сам отправляет ответ в Telegram: `POST https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/sendMessage`
  с `chat_id`, `text`, `reply_parameters: {"message_id": reply_to, "allow_sending_without_reply": true}`.
  Для этого нужен `TELEGRAM_BOT_TOKEN` в окружении;
- затем шлёт боту `{"result": <объект Message из ответа Telegram>}` на `callback.url` с `X-Callback-Token`.

**Реализовывать только если без этого не обойтись.** Бот по умолчанию работает по протоколу 2, а при
протоколе 1 теряются форматирование, темы форума и память.

---

## 10. Настройка на стороне бота

1. Нейросеть → «Новый провайдер»:
   - тип **«Сервер очереди»**;
   - адрес `https://queue.example.com/v1/chat/completions`;
   - API-ключ — ключ из `API_KEYS`;
   - «Загрузить модели» → выбрать основную и резервные;
   - таймаут 10–15 с: это время только на постановку задания.
2. Настройки → Вебхук → «Токен для сервера очереди» → сгенерировать. Этот токен бот кладёт в
   `callback.token` каждого задания. Адрес колбэка показан на странице «Нейросеть».
3. Если у бота не задан публичный адрес, указать `BOT_CALLBACK_URL` и `BOT_CALLBACK_TOKEN` на сервере.
4. Резервный провайдер (например, облачный OpenAI-совместимый) с бо́льшим номером приоритета. Когда очередь отвечает
   `429`/`503`, бот уйдёт на него сам.

## 11. Приёмка

Автотесты (pytest, апстрим и бот замоканы):

1. Постановка: `202` + `status: "Added to queue"` быстрее 1 с; повтор с тем же `job_id` — тот же ответ, задание одно.
2. Неверный ключ → `401`; неизвестная модель → `400`; переполнение → `429` с `Retry-After`.
3. Синхронный режим (`chat_id: 0`): ответ OpenAI-формы, колбэка нет.
4. Результат приходит на `callback.url` с `X-Callback-Token`; в теле `job_id`, `chat_id`, `reply_to`, `thread_id`, `text`, `model`.
5. Один чат — одно задание: два задания одного чата выполняются по очереди, разных чатов — параллельно в пределах слотов.
6. Round-robin: 10 заданий чата A и 1 задание чата B — B не ждёт все 10.
7. `MAX_WAIT` → колбэк с `error_code: expired`; `DELETE` → `cancelled`; вытеснение → `superseded`.
8. Ошибка апстрима → второй апстрим; все упали → колбэк с `error_code: upstream_error`.
9. Колбэк: `5xx` → повторы с паузами; `403` → без повторов, `dead`; после доставки `result_text` стёрт.
10. Перезапуск: задания `queued` и `running` выполняются после старта, ни одно не потеряно.
11. `callback.url` вне белого списка → `400`, запрос наружу не делается.
12. Журнал не содержит текстов сообщений и токенов при `LOG_CONTENT=false`.
13. `GET /v1/models` — список из конфига, формат OpenAI.

Ручная проверка с ботом:

```bash
# постановка, как это делает бот
curl -s https://queue.example.com/v1/chat/completions \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"model":"qwen3-27b","messages":[{"role":"user","content":"Привет"}],
       "protocol":2,"delivery":"bot","job_id":"test-1","chat_id":-1001234567890,"reply_to":null,"thread_id":null,
       "callback":{"url":"https://bot.example.com/webhook/llm","token":"'$CB'"}}'
# → {"status":"Added to queue","job_id":"test-1",...}; через несколько секунд ответ придёт в чат

# проверка, как кнопка «Проверить» в боте
curl -s https://queue.example.com/v1/chat/completions -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" -d '{"model":"qwen3-27b","messages":[{"role":"user","content":"ping"}],"chat_id":0}'

# что бот примет как результат (для отладки колбэка)
curl -s https://bot.example.com/webhook/llm -H "X-Callback-Token: $CB" -H "Content-Type: application/json" \
  -d '{"job_id":"manual-1","chat_id":-1001234567890,"text":"Тест доставки"}'
```

В журнале бота (Журнал → канал `llm`) должны появиться «Queue result delivered» и, при ошибках, «Queue job failed».

## 12. Чего не делать

- Не ходить в Telegram в протоколе 2 и не хранить токен бота.
- Не обрезать, не форматировать и не чистить ответ модели — это делает бот.
- Не держать соединение с ботом открытым на время генерации: только `202` и колбэк.
- Не логировать тексты и секреты.
- Не терять задания при перезапуске и не доставлять один `job_id` дважды без необходимости (бот защищён, но это шум).
